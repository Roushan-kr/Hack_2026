Decentralized Peer-to-Peer Substrate (Zenoh)

Why Zenoh Over ROS2/DDS and Centralized Cloud

In smart logistics, central servers create a single point of failure (SPOF) and introduce WiFi dead-zone latency. ROS2 with standard DDS incurs heavy memory footprints (~100MB/node) and O(N2) multicast discovery chatter. Zenoh solves this with lightweight peer-to-peer pub/sub and distributed state mirrors.

Our Decentralized Architecture

Zero Central Server: Every robot runs an identical symmetric stack with local path planning, local neighbor state mirrors, and deterministic conflict rules.

Passive Read-Only Dashboard: Killing or disconnecting the dashboard has zero effect on robot decisions.

Traditional Centralized Baseline

Central Planner Bottleneck: Every route, intersection wait, and aisle permission is granted by a central cloud server.

Stop-and-Wait Serialization: Robots must come to complete halts and wait in sequential FIFO queues at shared intersections.

Contract Net Protocol (CNP) — Auctioneer-Free Task Allocation

How Tasks Are Allocated Without an Auctioneer

When a new warehouse task is generated, it is broadcast to fleet/task/announce/<id>. In traditional systems, a central auctioneer tallies bids. In our decentralized system, every robot independently evaluates all received bids using the identical deterministic score function.

Bid Score = Distance to Pickup + (100 - Battery%) × 0.10 + Current_Load × 2.0

Two-Layer Conflict Resolution

Layer A (Macro Traffic Optimization) vs Layer B (Safety Net)

Layer A — Reservation Table (Macro)

Intent Mirroring: Robots publish intended (cell, timeslot) intervals along their planned BFS / A* routes.

Soft-Locks: Resolves intersection contention early so the yielding robot decelerates or detours before reaching the choke point.

Layer B — Local Avoidance (Micro Safety)

Zero-Collision Guarantee: Each robot runs a reciprocal collision check at every motion tick.

Priority Yield Rule: If two robots end up in adjacent contested cells, the lower-priority robot holds while the higher-priority proceeds.

Deterministic Priority Tuple Rule

When two robots contend for the same cell, there is no negotiation chatter. Each robot compares their priority tuples lexicographically:

// Priority Tuple: [task_urgency, distance_to_goal, robot_id] // 1. task_urgency: 0 if carrying cargo (dropoff phase), 1 if moving empty (pickup phase) // 2. distance_to_goal: shorter distance to completion wins // 3. robot_id: strict alphabetical tie-breaker (e.g., 'R1' < 'R2') function comparePriority(a, b) { if (a.urgency !== b.urgency) return a.urgency - b.urgency; if (a.dist !== b.dist) return a.dist - b.dist; return a.id.localeCompare(b.id); }

Chokepoints, Aisle Tokens & Anti-Deadlock Engine

How Head-On Deadlocks Are Solved at Bottlenecks

In warehouses with narrow single-lane corridors (e.g. cells (8,5) and (9,5)), head-on collisions and deadlocks can occur if opposing robots enter simultaneously.

1. Directional Aisle Tokens

Corridor cells maintain a token { owner, direction }. Entering robots claim the token. Opposing traffic automatically queues at the entrance boundary until the corridor and exit zone are cleared.

2. Proactive Anti-Deadlock Detours

If a robot is stalled for ≥ 2 ticks by stationary traffic, it automatically runs an anti-deadlock BFS path replan that penalizes stationary obstacle cells and routes via alternate open paths.
